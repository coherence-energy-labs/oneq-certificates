1. Paper 1 has a real error in its central decoder-comparison experiment
This is the highest-priority technical correction. It affects §VIII, Table V, and Figure 3.

The experiment represents a BP-OSD answer using component variables. Several variables can correspond to the same edge in the matching graph. To turn that answer into a graph correction, repeated edges must be combined modulo two: selecting the same edge twice cancels it.

The released scorer instead adds the graph-edge weight for every selected component, including repeated selections that cancel. It reduces the syndrome modulo two but does not reduce the cost in the same way. The relevant functions are dem_mechanisms and odd_and_weight in the released experiment script.

For component selections \(x_j\), the graph correction should be
\[
y_e=\left(\sum_{j:e(j)=e}x_j\right)\bmod 2,
\qquad
w(y)=\sum_e w_e y_e.
\]
The released computation instead sums the edge weight once per selected component. These quantities can differ dramatically.
An exact, reproducible counterexample
On a distance-3, three-round instance with syndrome [7, 9, 10], BP-OSD selects the edge (7, 10) nine times and the edge from 9 to the boundary once.

Nine copies of (7, 10) reduce to one copy.
Quantity	Value
Cost reported by the released scorer	44.3621835074505
Cost of the actual XOR-reduced graph correction	7.543721817379714
Artificial excess introduced by duplicate counting	36.81846169007079
Actual optimality gap of the projected correction	Exactly zero


The last line is supported by an attaining cut-packing witness accepted by the released exact checker. The projected correction is optimal on that graph.

The bundle contains the frozen graph, syndrome, correction, and certificate. Replaying that example requires neither a new BP-OSD run nor a new certificate search.

I also traced the experiment to its historical producing revision. The relevant functions have the same behavior there, so this affects the provenance of the reported results.

What needs to change: project component selections onto graph edges modulo two, verify the projected syndrome, compute the projected cost exactly, and regenerate the affected tables, plots, and summary statistics. I would preserve both the selected component vector and the projected edge set in future experimental records.

The core cut-packing certificate argument remains useful. The affected comparison currently assigns the wrong cost to some candidate corrections.
The decoder model is also described too strongly
The same section says BP-OSD maximizes likelihood over the full hypergraph. The implementation splits decomposed detector-error-model components into independent variables, losing the original event correlations. Finite BP with bounded OSD also does not generally guarantee an exact maximum-likelihood answer.

This requires a separate correction from the duplicate-counting fix. The manuscript should describe the independent-component approximation actually used, or the experiment should preserve full detector-error events as variables and document the subsequent graph projection.
2. Paper 3’s “new” distance values need to be reconciled with earlier public results
I found earlier public reports of the morphing distances highlighted as new in Paper 3.

The relevant evidence is an earlier public release, rather than just dates inside working notes:
- The gross-code-distance-12 v2.0 release was published on October 24, 2026 UTC, before these November 3 manuscripts.
- Its pinned E-017 audit explicitly reports circuit distance 12 for the relevant morphing construction with end-cycle parameters \([[144,12,12]]\), including both bases, noisy boundaries, and an all-rounds claim.
- Its pinned E-019 audit also reports the \([[72,12,6]]\) end-code distances 6/6 and discusses the associated family and folding conditions.
That makes the current numerical novelty wording unsupported without a careful comparison to these records.

There can still be a substantial contribution here: independent certification, a different certificate calculus, a clearer formal argument, independently reconstructed models, or additional specified instances. Those contributions should be stated directly.

The revision should identify, result by result:
1. Which numerical values were already publicly reported.
2. What is independently verified here.
3. Which model assumptions, schedules, or instances differ.
4. Which additional results remain new.
I did not rerun the earlier repository’s entire computation. I verified its public release provenance and the relevant reported results. This finding concerns the manuscript’s novelty claim; it does not establish anything about private discovery history or copying. I also did not establish that all 14 additional 2026 instances duplicate prior results.
3. Paper 3 needs corrections to a theorem and to its code comparison
Theorem 2 omits a necessary hypothesis
The standalone theorem on page 7 describes matching noise in mirrored expansion and contraction layers. The supplementary proof requires something stronger: the corresponding fault-image sets must coincide after propagation to the common mid-cycle representation.

Those conditions are different. A CNOT can propagate a local \(X\) fault into a two-qubit \(XX\) fault. Identical raw noise channels at two mirrored locations therefore need not produce identical propagated fault sets.

I constructed a counterexample using the same morphing gate structure with identical local-\(X\) noise on selected mirrored layers:
- The one-round model has no undetectable logical fault in its generated fault space.
- The two-round model has an explicit undetectable logical fault of weight 12.
Thus, the broad distance-equality statement does not follow from raw mirrored-noise equality alone.

The important qualification: the reported depolarizing instances satisfy the stronger condition used in the supplement. This finding does not refute their reported distance values. It means the theorem in the paper needs to state the condition its proof actually uses.

The clean repair is to require equality of the propagated fault-image sets, or to state a sufficiently precise conjugation-invariant noise condition that implies it.
“Same code” is incorrect in the highlighted comparison
In §VI C, the paper compares an IBM cycle with the morphing construction as if they operate on the same code.

They share the parameters \([[144,12,12]]\), but the released constructions have different stabilizer groups.

A particularly clear distinction is:
- The gross-code construction has weight-6 \(X\) and \(Z\) generators, and its stabilizers have even weight.
- The morphing end-cycle construction contains weight-9 stabilizers.
That also rules out equivalence under qubit permutations and local Clifford operations, which preserve Pauli weight.

The sentence should say “same parameters,” and the discussion should identify the distinct codes. The comparison cannot isolate the effect of a schedule change on a fixed code.

This correction is separate from the paper’s genuinely fixed-code CNOT-order comparisons, which remain meaningful. The earlier E-017 report also explicitly distinguishes the morphing end-cycle code from the gross code.
Some certificate scope is missing from the table description
The 22 IBM proof files establish a scoped statement about light irreducible logical faults whose earliest detector round lies in the specified initial window. The global conclusion uses those proofs together with the window argument.

Table I identifies analogous scope for other families but does not adequately identify it for IBM. The caption should make that dependency explicit.

The certificates themselves verified; the issue is accurately stating what an individual certificate proves.
4. Paper 2 has reproducible checker-contract defects
These issues deserve attention because small, strict checkers are part of the claimed trust boundary.
Input validation differs between checkers
Input	Observed behavior	Required correction
Syndrome containing 2	The independent tree reference checker reduces it with & 1 and accepts an example that the production checker rejects.	Reject nonbinary syndrome entries before any reduction.
Fractional index 0.9 in a check support	The production flat checker converts it to 0 and accepts malformed input; the reference flat checker rejects it.	Require lossless integer validation before conversion.
Integral floats and booleans	Acceptance rules are inconsistent across helpers and implementations.	State and enforce one precise input-domain contract.


Paper 2 says the checkers now refuse nonbinary syndromes. The reference tree checker is a concrete exception.

The reproducer includes a tiny example with a syndrome of [2]; its acceptance does not require a large or complicated proof.
Bound-only mode returns an unjustified optimality result
There is also an API semantics problem in check_qldpc_bnb.

A bound-only call can correctly establish its requested threshold statement while returning:
- "EXACT-OPTIMAL",
- a purported primal weight,
- and an objective value derived from an internal threshold.
For a one-variable instance with true optimum 2, the reproduced bound-only call reports objective 1. An infeasible instance can likewise receive a finite reported objective.

The checked lower-bound statement can still be valid. The returned optimality and primal fields are the problem.

The appropriate result is a distinct status such as LOWER_BOUND_PROVEN, with no claimed primal optimum unless a feasible attaining candidate has also been checked.

Current distance and frame callers appear to use only the acceptance flag, so I did not establish that this API defect corrupted a published numerical result. It does, however, create a misleading interface for future callers.

The valid stored receipt corpus passed in full. These defects concern malformed-input handling and the meaning of returned results.
5. The released tests have a real portability failure—and a small tested repair
The initial test run produced 256 passes and 8 failures.

One failure was a missing optional SAT dependency. After installing it, the remaining seven failures came from platform-dependent line endings in exported model files:
- Archived files use Windows CRLF line endings.
- The exporters use ordinary text output.
- Linux produces LF line endings.
- The resulting bytes fail the archived SHA-256 checks despite representing the same rows.
For an IBM model, the fresh export was 17,340 bytes and the archived model 18,350 bytes. The 1,010-byte difference is exactly the line-ending difference. Converting LF to CRLF reproduced the archived bytes exactly. The same explanation held across the other inspected samples.

I tested an isolated two-line patch that explicitly fixes the encoding and line endings in the two exporters:
with open(out, "w", encoding="ascii", newline="\r\n") as f:


With that patch and the required dependencies, all 264 tests passed.

The patch is included in the bundle. The public repository was not changed.

For a release whose identity and reproducibility rely on exact hashes, serialization needs a defined byte format. The repair should preserve hash verification and make exported bytes deterministic.
6. Several empirical and wording claims need tighter interpretation
These are less severe than the scoring defect, but they affect what readers can reasonably conclude.
“Exact” candidate equality sometimes means “within \(10^{-9}\)”
Paper 1’s experiment uses tolerance checks such as abs(arr) < 1e-9 to classify zero gaps.

An exactly verified reference certificate does not automatically make a floating-point candidate comparison exact.

If the paper calls the resulting fraction “exact,” candidate costs should be computed using the same exact rational interpretation and compared exactly. Otherwise, the text should say that the gap is below the stated tolerance.

When the reference is only certified within \(\varepsilon\), a candidate’s true gap lies in the interval
\[
\left[w(K)-w(J),\; w(K)-w(J)+\varepsilon\right].
\]
That distinction should be preserved in plots and classifications.
BP scaling substantially changes the strength of the baseline
Paper 2’s stress results show how consequential the baseline configuration is:
Baseline configuration	Reported stress misses
Unscaled BP baseline	178/300
BP scaling of 0.625	1/300


The paired logical comparison against the scaled baseline has three discordant losses versus zero, with the reported two-sided exact \(p=0.25\).

That supports a much more cautious statement about logical-performance improvement against the tuned baseline than the unscaled comparison suggests. The certification and repair capability can be valuable even when a strong logical-performance advantage has not been established.
One measured observable does not establish whole-block logical performance
The zero-error result on 149 trials concerns the selected observable. A zero count gives a one-sided 95% upper bound of approximately 1.99% for that measured failure probability under the stated sampling interpretation.

It does not establish zero failure probability, performance on all 12 logical qubits, or a block-level superiority claim.

The manuscript should keep these quantities distinct:
- Optimality of the decoded error under the chosen objective.
- Correctness of a selected logical observable.
- Failure of any logical degree of freedom in the block.
Proof-format statistics need consistent categories
The Paper 2 counts reconcile, but different percentages answer different questions:
- 2,002/2,019 = 99.16% use flat receipts.
- Including the eight one-node trees, 2,010/2,019 = 99.55% require no branching.
A one-node tree and a flat certificate can both establish optimality without a branching search. The paper should distinguish proof format, whether branching occurred, and whether the original BP answer was retained.
The prior-work discussion should distinguish exact certification methods more carefully
The related-work treatment compresses different objectives and certification methods too aggressively. In particular, the cited certified-decoding work includes a deterministic MBE branch with reported small-code certification times around 5–26 seconds. The approximately 272-second gross-code result does not provide the deterministic certificates that a broad “exact certificates take minutes” characterization would suggest. The revision should distinguish code size, objective, and deterministic versus probabilistic certification. researchgate.net

Minimum-weight error certification and maximum-likelihood logical-coset certification also solve different optimization problems. Comparisons should make that distinction explicit.

8. Limits of this audit
The scope matters when interpreting those successful results.

I did not:
- Replay the entire million-shot archive.
- Replay the complete Willow development archive.
- Regenerate the 30 large distance proofs that were not shipped, including all three-colour lower-bound proofs and four morph144 proofs.
- Perform a fresh Lean/Mathlib kernel build.
- Reproduce every original stochastic experiment with the original Windows environment and random samples.
Accordingly, “all 274 shipped distance certificates verified” is the supported statement. I cannot extend that to all 304 claimed proof instances or to a fresh formal verification of the C implementation.

Publishing the remaining large proofs as release assets would make the distance claims materially easier to audit.
Recommended revision order
1. Repair Paper 1’s correction projection and cost calculation, then regenerate the affected experiments. The current comparison numbers should not be retained without that rerun.
2. Revise Paper 3’s abstract, introduction, and novelty statements against the earlier public results. Preserve clearly identified independent-certification contributions.
3. Correct Paper 3’s theorem hypothesis and “same code” comparison. Make the scope of the IBM certificates explicit.
4. Harden the checker input contracts and separate bound-only results from exact-optimality results. Add focused regression cases for the reproduced failures.
5. Make model serialization deterministic and fix the reproduction instructions. The tested patch demonstrates that the current portability failures are straightforward to resolve.
6. Tighten the empirical conclusions. Distinguish exact equality from tolerance, tuned from untuned baselines, individual-observable performance from block performance, and proof format from search effort.
My assessment is that the strongest contribution—the ability to validate substantial optimization and distance claims through independently checkable evidence—has real support. The current papers overstate some experimental, theoretical, and novelty conclusions. The report identifies the repairs needed to bring those claims into line with the evidence, with reproducible examples for the most consequential defects.
